# PC维护工具箱 —— 设计文档

状态：待人工批准
日期：2026-10-24

## 意图与背景（Intent & Why）

这是一个业余时间推进的 Windows Store 侧项目，没有固定上线时间压力。作者现有一个
推广渠道：一位做游戏的朋友可以帮忙把 App 在 Microsoft Store 的"应用"分类榜单/排名
曝光度提升，具体是哪个榜单尚不确定，按"任意榜单都可能"来设计。作者目前没有现成的
用户群，游戏内容本身的变现能力这两年变弱，希望转向"卖铲子"模式：靠效率/维护类工具
赚钱，而不是靠游戏内容本身。

商业模式：免费核心功能获客（靠榜单曝光），付费解锁高级功能（Pro 一次性解锁，不走
订阅）。较大/较复杂的功能（PDF编辑、本地LLM、AI抠图、AI OCR、FTP Server、图片格式
转换、winget管理等）明确放到后面，可能做成独立App，通过本App互相导流，不在本阶段
范围内。

经过多轮市场调研（Microsoft Store 评分/评论数据、国内软件下载/评测站 ghxi.com、
423down.com、sspai.com，cn.softmany.com 作为补充），确定第一个产品方向：**PC维护
工具箱**——把磁盘空间分析、右键菜单管理、卸载工具三个功能捆绑进一个App。
原始候选的"重复文件查找"已经过讨论，本阶段**明确不做**。

选择这三者的依据：
- 三个独立信息源（Microsoft Store付费产品、国内下载站竞品密度、少数派等编辑向媒体
  的反复推荐）交叉验证了需求的真实存在。
- 技术上都不需要联网、不需要AI、不涉及GPL组件强制传染（见"约束"一节），复杂度可控，
  适合业余时间推进的第一个产品。
- 三者可以共享底层"扫描结果"数据模型和部分依赖（见"已决定的实现方式"），不是三套
  独立工程。

## 目标（Goals）

1. 做出一个可以上架 Microsoft Store 的 MVP，捆绑磁盘空间分析、右键菜单管理、卸载
   工具三个模块。
2. 免费版驱动安装量/榜单曝光，付费Pro解锁驱动营收。
3. 磁盘空间分析不与 WizTree/TreeSize/SpaceSniffer 拼"扫描速度"（这条路已被免费的
   WizTree 走到头），改做它们都没做好的两个差异化点：
   - 跨次扫描历史对比（"这周空间涨了多少，涨在哪"）
   - 游戏/大型应用专属视图（优先支持 Steam 库解析，占用空间+多久没动过+一键卸载），
     呼应"卖铲子给游戏玩家"的定位
4. 卸载工具统一处理三种安装机制（Steam 游戏 / 普通 Win32 程序 / Microsoft Store
   MSIX 应用），对用户呈现一个统一入口。
5. 右键菜单管理提供安全的（可恢复的）菜单项启用/禁用，并附带一个高性价比的"一键
   恢复完整/经典右键菜单"快捷开关（应对 Windows 11 "显示更多选项"这个被广泛吐槽
   的双层菜单问题）。
6. 优先参考/复用宽松许可证（MIT/Apache 2.0）的开源项目实现思路或代码，避免把 GPL
   许可证的参考项目代码直接编译进本项目。

## 非目标（Non-goals，本阶段不做）

- 不做重复文件查找。
- 不做本地LLM、AI抠图、AI OCR、PDF编辑、FTP Server、图片格式转换、winget GUI管理
  ——这些留到以后，可能做成独立App。
- 不在MVP阶段实现 NTFS MFT 直读的"极速扫描"模式；MVP用标准递归遍历，够用即可，
  这个优化留到产品验证成功之后再做。
- 不在本阶段搭建**对外的**第三方插件分发/沙箱基础设施（WASM运行时托管、插件市场、
  插件安全审核流程）——这些留到真正需要对外开放扩展能力时再做。但内部架构会按
  "模块化、松耦合"的方式设计（见"已决定的实现方式"），为以后可能的插件化改造
  预留接口，不是现在就要重写模块边界。
- 不针对 ReFS/FAT32/exFAT 做特殊优化，统一走标准遍历兜底。

## 反目标（Anti-goals：哪怕技术上做成了，也算失败）

- 做成"又一个无差异化的通用磁盘分析器"，用户用完觉得"这跟WizTree有什么区别"。
- 右键菜单的禁用操作或卸载残留清理做得不安全（直接删除而非可恢复），导致用户系统
  出问题、引发差评甚至被当成"流氓软件"举报。
- 因为"卸载工具"这个品类触发 Microsoft Store 的敏感审核政策而被卡审核，且没有
  提前做好测试/缓冲。
- 在验证基本的产品-市场契合度之前，过早引入复杂架构（完整WASM插件沙箱、AI推理
  基础设施），拖慢交付。

## 约束（Constraints）

- 单人开发、业余时间推进、没有固定截止日期。
- 必须打包为 MSIX，声明 `runFullTrust` 能力，走 Microsoft Store 的 Desktop Bridge
  全信任应用路径。
- 技术栈：.NET 8，WinUI3 或 WPF，有条件的地方用 Native AOT（沿用此前已确定的
  架构方向）。
- 不把 GPL 许可证项目（ContextMenuManager、ContextMenuMgr 均为 GPLv3）的代码直接
  编译进本项目；可以参考其功能设计思路，但实现要自己写。
- 优先选用 MIT/Apache 2.0 的参考实现：
  - Bulk Crap Uninstaller（Apache 2.0）——卸载/残留扫描逻辑的主要参考对象，
    官方声明允许免费商用无义务，可直接借鉴甚至复用代码。
  - LordMike/NtfsLib（MIT，已停止维护但可fork）——未来做 NTFS 极速扫描时的参考。
- 推广渠道：一位朋友可以帮助提升 Store"应用"分类下的榜单排名，具体榜单类别未定，
  按"任意榜单"设计，不针对某个垂直用户群做特别优化。
- 目标市场/语言：此前所有市场调研（ghxi.com/423down.com/sspai.com）和定价（¥）都是中国市场语境。作者决定：V1 以**简体中文/中国区 Store** 为主要目标，不强求V1 就做英文本地化；但 CLSID→友好名称查找这类逐语言相关的部分，实现时要设计得足够通用，不硬编码只认中文系统，方便以后加英文支持不用重做架构。
- 定价：免费核心功能 + 一次性付费解锁 Pro（¥18-30 量级），不做订阅制，降低用户
  决策成本。
- 权限模型：App 本身以普通用户权限运行，不整体要求管理员权限（不用
  `requireAdministrator`）。只有真正需要动系统级文件/HKLM注册表的操作（卸载残留
  清理、部分右键菜单项）才临时拉起一个提权的小帮手进程，用完即退出，日常使用不
  会被UAC打扰。
- 系统版本：**只支持 Windows 11**，不考虑 Windows 10 兼容（"一键恢复经典右键
  菜单"本身就是Win11才有的问题，Win10用户也快到生命周期尾声）。这也意味着可以
  放心用 WinUI3，不需要为了兼容Win10退回WPF。

## 考虑过的方案（Approaches）

1. **第一个产品该做什么**：在"单点简单工具"（PNG转ICO、剪贴板管理、文件预览、
   截图OCR、FTP、winget管理、PDF编辑等）与"捆绑的PC维护工具箱"之间做选择。
   选择了捆绑方案，因为三个独立信息源交叉验证了需求，且技术复杂度低、可共享底层
   实现，推广资源集中在一个App上比分散成多个曝光不足的独立App更有效。
2. **磁盘分析器的核心卖点**：在"拼扫描速度（NTFS MFT直读）"与"做差异化功能
   （历史对比+游戏专属视图）"之间选择。放弃拼速度（WizTree已经免费做到最快，
   Windows系统本身也在补强基础的"大文件在哪"场景），选择差异化功能路线。
3. **NTFS极速扫描的实现时机**：在"MVP就做"与"MVP先用标准遍历、以后再加"之间选择。
   选择后者，因为MFT直读需要管理员权限、只对NTFS有效、工程复杂度不低，不适合作为
   第一个里程碑的必需项。
4. **右键菜单管理的实现方式**：在"直接用GPL开源项目代码"与"参考其功能设计后自己
   独立实现"之间选择。选择后者，因为这个功能技术难度本身不高，自己写的成本低于
   处理GPL许可证边界的麻烦。
5. **卸载残留检测的技术方案**：在"猜测常见残留路径"与"卸载前后快照对比"（Revo
   Uninstaller同款技术）之间选择。选择快照对比，同时吸取其他用户对Revo的真实反馈
   （残留结果堆成几万条让人无从下手），决定对结果做分组/过滤展示，而不是甩给用户
   一份原始diff列表。
6. **三种应用的卸载路径**：统一一个"卸载"入口，背后按应用类型路由到三种机制
   （Steam协议 / Win32注册表卸载字符串+快照对比 / MSIX的PackageManager API），
   用户不需要感知背后的差异。

## 已决定的实现方式（The parts of the how they decided）

- **共享数据模型**：磁盘分析模块的 Treemap 视图、历史对比视图、游戏与大型应用
  视图，三个界面共用同一套"扫描快照"数据结构（文件夹路径、大小、修改时间、项目
  数），只是展示方式不同，底层扫描逻辑只写一次。
- **磁盘分析模块内部开发顺序**：
  1. 基础 Treemap 扫描（标准递归遍历，多线程）
  2. 手动触发的"与上次扫描对比"功能（本地存快照，diff排序）
  3. Steam游戏专属视图（解析 `libraryfolders.vdf` / `appmanifest_*.acf`，
     卸载按钮走 `steam://uninstall/<appid>`）
  4. 非Steam大型应用的兜底识别（文件夹大小排名+注册表Uninstall项匹配友好名称）
     ——优先级最低，V1可以不做
- **右键菜单管理模块**：
  - 枚举 `HKEY_CLASSES_ROOT\*\shellex\ContextMenuHandlers`、
    `Directory\Background\shellex\ContextMenuHandlers` 等注册表路径
  - CLSID 转友好名称（查 `InprocServer32` 指向的DLL路径再读文件描述信息）
  - 禁用操作只增删我们自己写的值而不删除任何键（2026-10-25 更新，经真实 Explorer 验证，见 `2026-10-25-context-menu-mechanism-spike.md`）：处理程序用当前用户的 `Shell Extensions\Blocked` 列表，静态动词用 `HKCU` 里的 `LegacyDisable` 值；删掉这些值即可恢复，不需要管理员权限。原先设想的"重命名/移动备份"留作需要提权时的回退方案
  - 附带一键"强制显示完整/经典右键菜单"的快捷开关（修改
    `HKCU\Software\Classes\CLSID\{86ca1aa0-34aa-4e8b-a509-50c905bae2a2}\InprocServer32`）
- **卸载工具模块**：
  - 统一的"已安装项目"列表，背后按来源路由到三条路径：
    - Steam游戏 → `steam://uninstall/<appid>`
    - 普通Win32程序 → 注册表卸载字符串 + 卸载前后快照对比找残留，结果按文件夹/
      注册表路径分组展示供用户审核后删除
    - Microsoft Store (MSIX) 应用 → `Windows.Management.Deployment.PackageManager
      .RemovePackageAsync`
  - 与未来的 winget 模块共享 `PackageManager` 这个依赖（本阶段winget模块不做，
    但实现时注意接口预留）
- **内部模块化设计（为未来插件化留好接口，但本阶段不搭建插件分发/沙箱基础设施）**：
  三个模块（磁盘分析、右键菜单管理、卸载工具）各自实现为独立的、松耦合的组件
  （比如各自是一个独立类库，有清晰的内部接口：初始化、获取UI、执行操作），彼此之间
  通过明确定义的事件/消息契约通信，不互相直接引用对方的内部实现细节。核心扫描/操作
  逻辑（引擎层）要和UI展示层分开，不要把业务逻辑直接写在WinUI3的页面代码里。这样做
  的好处是：即使现在不搭建WASM沙箱/插件市场，以后如果真要把某个模块拆成对外插件
  （或者反过来接入别人的模块），改动范围只是"换一种方式加载这个组件"，不需要把
  整个App的模块边界推倒重来。
- **整体模块开发顺序**：磁盘分析（最简单，Store曝光的"门面"）→ 右键菜单管理
  （次简单，用来验证付费转化）→ 卸载工具（复用磁盘分析模块已有的扫描基础设施，
  增加三条卸载路由）
- **免费/付费分层**：
  - 磁盘空间分析：整体免费（获客用）
  - 右键菜单管理：免费=查看/启用禁用 + 一键"恢复完整/经典右键菜单"快捷开关（作者决定：这是本模块曝光力最强的钩子功能，保持免费，呼应"免费引流、复杂功能才付费"的整体策略）；付费=自定义添加菜单项、批量"一键清理"
  - 卸载工具：免费=基础卸载；付费=强制残留清理、批量卸载

## 留给实现者决定的部分（What's left to the builder）

- MSIX manifest 的具体能力声明，以及第一次 Store 提审的实测结果（这是最大的
  未知风险，建议尽早用一个空壳App验证一遍提审流程）
- 具体UI视觉设计（没有做过原型/视觉稿，目前只有交互逻辑层面的讨论）
- CLSID→友好名称数据库的具体来源（自建一个小型精选库，还是有无许可证兼容的
  现成开放数据集可用）
- Windows 11"新/旧"右键菜单共存情况下的具体注册表路径处理细节
- 卸载残留扫描结果的具体分组/过滤算法细节
- 非Steam大型应用识别的兜底逻辑（已标注为低优先级，V1可以跳过）
- 付费解锁的具体实现机制（Store内购 vs 自建许可证验证）
- 第一次Store提审的测试计划，特别留意"卸载工具"类目是否触发额外审核关注
