# 下载文件夹整理模块 —— 设计文档

状态：待人工批准
日期：2026-10-29
调研依据：`2026-10-29-win11-tidy-pain-points-research.md`（第 5–7 节）

> 标记约定：**【定】** = 作者在对话里明确决定；**【我的提议】** = 设计者补的默认值，作者没有明确说过，可以推翻。

## 意图与背景

TidyBox 现有三个模块（磁盘分析、右键菜单、卸载）加一个与"整理"无关的词汇条。本设计增加第四个模块，帮 Windows 11 用户整理**下载文件夹**。

为什么做：
- 下载文件夹乱是调研里证据最强的"整理"痛点（Reddit 多个帖子，且多是"我自己写了个小工具"）。
- 但"按类型把文件分进子文件夹"这件事已经拥挤：Mouzi（免费开源，已有预览、撤销、三种模式）、File Juggler、SortSage、DropIt 等。光做这个没有差异化。
- 调研里**有人明确提出、对手承认合适、但没人实现**的需求只有一个：整理完以后，分类文件夹里的旧安装包、压缩包会重新堆满，需要"文件老化 + 回顾队列"（Mouzi issue #62，维护者回复"很适合，但太大、未排期"）。
- 竞品的信任问题是真实的：Mouzi 首次启动就自动整理了用户没配置过的文件（#69）；其 Windows 安装包被 Defender 拦截（#65，在等代码签名证书）。TidyBox 走 Microsoft Store 的 MSIX 分发，天然在这一点上占优（**推断，未核实 Store 审核结果**）。
- TidyBox 已有的磁盘占用视角和回收站能力，可以让"回顾"比单纯整理工具更有价值。

商业背景沿用 `2026-10-24-pc-maintenance-toolbox-design.md`：免费功能获客，一次性付费 Pro，不走订阅。

## 目标（Goals）

1. **【定】只做下载文件夹**。不做桌面。
2. **【定】做法 C：一个模块，"整理"和"回顾"共用同一个文件级扫描器和同一份日志。**
3. **【定】界面 B：一页往下滚，上方"① 可以整理的"，下方"② 久未动的"，顶部是汇总。**
4. **【定】回顾里每个文件有两个动作：移到回收站；保留，不再提醒。**
5. **【定】MVP 全部免费，包括撤销。Pro 以后再加。**
6. 整理的核心闭环：扫描 → 按类型出提案 → 预览（可勾选）→ 移动 → 记录日志 → 可按批次撤销。
7. 回顾的核心闭环：列出久未动的文件 → 用户勾选 → 移到回收站；或标记"保留"后不再出现。

## 非目标（MVP 不做）

- 桌面整理（OneDrive 重定向、快捷方式、免费竞品和国内管家软件自带，调研结论是进入难度更高）。
- **后台监控、托盘、开机自启、自动移动。** 首版只在用户打开页面时扫描。（调研里 organize 最高赞的 issue 是"Watch folder?"，说明用户确实想要自动化；恐惧点是"没预览就动文件"。后续可以做"只收集进待批准队列、不移动"的监控，见"后续"。）
- 自定义规则编辑、规则导入导出（放 Pro）。
- 云端或本地 AI 分类、内容识别、OCR、EXIF 日期归档、自动解压。
- 标签系统（V2EX 里有人提出"一个文件属于多类"，但那是另一个产品）。
- 跨磁盘移动。MVP 的目标子文件夹都在下载文件夹内部，天然同一磁盘。
- "已安装软件的安装包"识别（见下"后续"，需要先做命中率原型）。
- 对下载文件夹整体做重复文件扫描。只在移动时对同名冲突比较内容。

## 反目标（做成了也算失败）

- 没有用户明确确认，就移动或删除了任何文件。
- 撤销悄悄失败、覆盖了用户的文件，或丢了文件。
- 像 Mouzi 那样出现"Others"杂物堆：没有匹配规则的文件必须**留在原处**，并在界面里说明。
- 回顾列表每次打开都把同样的旧文件再列一遍，用户学会忽略它。
- "释放空间"的提示不诚实：移到回收站不等于释放空间（沿用 `2026-10-26-disk-space-reclaim-features-design.md` §0 的结论，界面必须说明"清空回收站后才真正释放"，并复用已有的清空入口）。
- 又一个和 Mouzi 没区别的整理器。

## 约束

- 只支持 Windows 11；.NET 8；WinUI 3 外壳；MSIX + `runFullTrust`。
- 以普通用户权限运行，不需要提权帮手。
- 模块松耦合：引擎与 UI 分开，新模块不直接引用其他模块的内部实现（见 `2026-10-24-pc-maintenance-toolbox-design.md`）。
- 本地存储只用 JSON，放在 `%LOCALAPPDATA%\TidyBox\<模块>\`，不引入 SQLite（与 `2026-10-26` 设计的结论一致）。
- 不联网、不上报。
- 现有 App 外壳是 **32 位（x86）进程**（`IRecycleBin.cs` 注释里记录了 SHQUERYRBINFO 因此踩过坑）：新增任何 P/Invoke 结构体时必须考虑位数。
- V1 以简体中文为主，但目标文件夹名、规则名不得硬编码在逻辑里，要走资源，避免以后加英文要重做。
- 不得把 GPL 代码编译进来。Mouzi 和 organize 为 MIT，可参考思路；使用其代码需保留版权声明并更新 `THIRD-PARTY-NOTICES.md`。

## 考虑过的方案

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| A. 整理优先 | 新模块，核心是分类、预览、移动、撤销 | 一看就懂，需求最广 | 与 Mouzi 差异小 |
| B. 回顾优先 | 新模块，核心是旧文件回顾队列 | 差异最大 | 价值不如整理直观；"整理"卖点变弱 |
| **C. 一屏两部分（选定）** | 共用扫描器与日志，页面分整理、回顾两部分 | 先让用户理解，再靠回顾拉开差距 | 工作量最大 |

**【定】选 C。** 理由：调研显示用户想要的是一个习惯（例如"每周五花 20 分钟整理下载文件夹"），而不是一次性分类；但"整理"最容易被理解，所以两者放在一页。这个理由基于很少的证据（一篇小红书笔记、Mouzi #62、一个 V2EX 帖子）。

**否决：并入现有磁盘分析模块。** 它的扫描按子文件夹聚合，没有逐文件信息；改它会牵动已有测试，并违背模块松耦合约定。

## 已决定的实现方式

### 与现有代码的接入点（已核对）

- 新项目 `TidyBox.Modules.Downloads`（名称为我的提议），实现 `IToolModule`。
- 在 `App.xaml.cs` 构造函数里 `Modules.Register(new DownloadsModule())`。
- 在 `MainWindow.xaml.cs` 的 `Pages` 和 `ModuleIcons` 两个字典里各加一项；视图放在 `TidyBox.App/Views/`。
- 存储目录参考 `DiskAnalyzerModule`：构造函数接受可覆盖的目录，`InitializeAsync` 里创建并在失败时抛出，让外壳显示"加载失败"。
- 单元测试项目 `tests/TidyBox.Modules.Downloads.Tests`，与现有模块一致。
- **`IRecycleBin` 目前只有 `Delete(folderPath)`，只能删文件夹。** 需要新增文件版本（我的提议：在同一接口上加一个方法，沿用 `FileSystem.DeleteFile(..., RecycleOption.SendToRecycleBin)`）。
- **`ByteSizeFormatter` 目前在 DiskAnalyzer 模块里。** 新模块不应引用磁盘分析模块；建议像之前把 `IRecycleBin` 移到 Core 那样，把它移到 `TidyBox.Core`（**【我的提议】**，施工者可以改成复制一份，但要说明）。
- 安全约定沿用 `DiskAnalyzerModule` 的做法：任何会动文件的方法都要重新校验路径确实在允许的根目录（这里是下载文件夹）之下，防止过期或被篡改的请求。

### 界面（【定】B）

页面从上到下：
1. 标题与路径，汇总行（总占用、超过阈值的占用）。汇总里的"可释放"必须与回收站的诚实提示一致。
2. **① 可以整理的（N）**：按目标文件夹分组；每项显示文件名、人类可读大小（用 `ByteSizeFormatter`）、来源（有则显示）、冲突说明；**【定】没有风险的提案默认勾选**（一次确认摘要是明确确认的门槛，不会在用户没点按钮时动任何文件）；默认**不勾选**的只有：可疑项（双扩展名）、"不会动"的文件、回收批次类建议（例如内容相同的重复文件的源文件）。默认勾选与默认不勾选的分开显示；底部主按钮"检查所选操作（n）"。
3. **② 久未动的（N）· 可释放 X**：每项显示文件名、大小、天数、来源；默认**一项都不勾选**；两个动作：移到回收站、保留，不再提醒；
4. 底部折叠区"已保留（N）"，可以把某个文件放回提醒列表。
5. 底部"历史"：按批次展示整理记录，每批一键撤销。

没有匹配规则的文件：在 ① 里单独一组"不会动"，说明原因，不勾选。

### 整理（【我的提议】，除非另标）

- **扫描范围**：只扫下载文件夹顶层的**文件**；顶层的子文件夹整理时不动（用户的下载目录里经常有解压出来的整个项目，例如一个含 107 个文件的目录，移动它风险大于收益）。
- **下载文件夹路径**：用 Known Folder API 获取，不硬编码 `%USERPROFILE%\Downloads`，因为用户可能把它重定向到别的盘。
- **默认分类**（只按扩展名，一个扩展名只属于一个分类，所以没有优先级冲突；**没有"其它"兜底分类**）：
  - 图片：jpg、jpeg、png、gif、webp、bmp、svg、ico、heic、heif
  - 文档：pdf、doc、docx、xls、xlsx、ppt、pptx、txt、rtf、odt
  - 压缩包：zip、rar、7z、tar、gz、bz2、xz
  - 安装包：exe、msi、msix、appx
  - 音乐：mp3、wav、flac、aac、ogg、wma、m4a
  - 视频：mp4、avi、mkv、mov、wmv、flv、webm
  - 以上集合参考 Mouzi 的默认规则（截图所见）。`.md`、`.xpi`、`.apk` 等不在其中，会留在原处。
- **目标位置**：下载文件夹内的子文件夹，名称走资源（V1 中文）。若下载文件夹里已经有另一种语言命名的同类文件夹（例如 Mouzi 创建的 `Documents`），复用它还是新建，留给施工者决定（见"留给施工者"）。
- **安全过滤**（不进入提案）：未下载完的文件（`.crdownload`、`.part`、`.tmp` 等）、被其他进程占用的文件、最近一次写入距今不足 N 分钟（N 默认 5，参考 Mouzi）、0 KB、`desktop.ini`、`Thumbs.db`、重解析点（符号链接）。
- **可疑项默认不勾选**：MVP 只检查**双扩展名**（前一个扩展名是文档或图片、最后一个是可执行类，如 `invoice.pdf.exe`）。**不做内容（魔数）检测。**
- **同名冲突**：先比大小，大小相同再比内容哈希。内容相同 → 提案为"跳过"（建议把源文件移到回收站，由用户勾选）；内容不同 → 给新文件加后缀 `(n)`，**后缀只加一次，不能出现 `(1) (1)`**。
- **首次打开只扫描**，不移动任何东西。（Mouzi #69 的教训。）
- **执行**：用户勾选并点"检查所选操作"后，先出一次确认摘要（将移动多少项、总大小），确认后才执行。
- **同一磁盘**：目标都在下载文件夹内，因此是同卷重命名，不复制，也不会丢失 `Zone.Identifier`（已验证 Mouzi 的同类移动不丢；TidyBox 自己的移动在实现后必须同样验证）。

### 移动日志与撤销（【我的提议】）

- 每个批次一个 JSON 文件，放在 `%LOCALAPPDATA%\TidyBox\Downloads\journal\`。
- 每条记录：原路径、目标路径、大小、修改时间、触发的规则、结果。
- **撤销**按批次，逐项检查：目标文件还在、大小与修改时间和记录一致、原位置没有被别的文件占用。任何一项不满足就跳过这一项并在结果里说明，**绝不覆盖**。
- 批次分两种类型：**移动批次**（可一键撤销）和**回收批次**（只记录，**撤销要由用户从回收站手动还原**，界面必须如实说明，不假装能撤销）。一次用户操作如果既有移动又有回收，拆成两个批次分别记录和展示；"一键撤销"只出现在移动批次上。
- "内容相同的重复文件"的建议动作是把源文件移到回收站，因此属于回收批次，在界面上和普通移动分开显示。
- 日志损坏时按"没有历史"处理，不崩溃（与 `SnapshotStore` 一致）。
- 规模：下载文件夹可能有几万个文件。只扫顶层和分类文件夹一层，成本有上限；列表用虚拟化的控件；扫描要有进度和取消。哈希只在同名冲突时计算。
- 来源读取（`Zone.Identifier`）和下载文件夹路径（Known Folder）用托管代码或简单 P/Invoke 即可，**不需要 x64 辅助进程**；新增的 P/Invoke 结构体仍要照顾 32 位进程的布局。

### 回顾（【我的提议】，保留动作为【定】）

- **"多久没动"的时间**：取**创建时间与修改时间中较晚的一个**。实测（作者机器，118 个文件）：112 个两者相差不到 1 天，5 个修改时间比创建时间更早（解压或复制带来的旧时间）。单取修改时间会把刚解压出来的文件误判为"很久没动"。最后访问时间不用：Mouzi 维护者指出它不可靠，且 Windows 在 `DisableLastAccess=2`（系统管理）下也可能不更新。
- **阈值**：固定 90 天，MVP 不可配置。作者机器上，按这个阈值 118 个文件里有 47 个超过 90 天（约 40%）——说明列表会有相当长度，对噪音要特别小心（见下）。
- **范围**：下载文件夹**顶层的文件**，加上 **TidyBox 自己整理进去的那几个分类文件夹里的文件（只看一层）**。这样"整理完又堆满旧安装包"这个核心场景才被覆盖。不进入用户自己建的文件夹，也不进入别的工具建的文件夹（例如 Mouzi 建的 `Documents`），除非它恰好就是 TidyBox 复用的目标文件夹（见"留给施工者"）。顶层子文件夹如何计算年龄见"留给施工者"。
- **整理后年龄不重置**：已实测（2026-10-29，作者机器，PowerShell `Move-Item`）：同卷移动后创建时间、修改时间、`Zone.Identifier` 都保留。TidyBox 自己的移动实现后要有测试再确认一次。
- **动作**：移到回收站；保留，不再提醒。没有永久删除。
- **回顾同样套用整理的安全过滤**：未下载完的文件、被占用的文件、最近 5 分钟内写入的文件都不出现在回顾里，因为回收站动作比移动更具破坏性。
- **确认**：回顾里的"移到回收站"同样要出确认摘要（多少项、总大小，并说明"清空回收站后才真正释放空间"），批量确认一次，不逐个弹。
- **列表可用性**（约四成文件超过阈值，列表会很长）：默认按大小降序；提供按类型筛选，以及"全选当前筛选结果"。**默认仍一项都不勾选。**
- **保留的存储**：`%LOCALAPPDATA%\TidyBox\Downloads\kept.json`，以"完整路径 + 大小 + 修改时间"为键；文件被修改或换了位置就视为新文件，重新参与回顾。可以在"已保留"里放回。TidyBox 自己移动或撤销一个文件时，要**同步改写** `kept.json` 里对应条目的路径，否则整理一下，"保留"就失效。
- 与 `2026-10-26` 设计里的 `ignoredItems`（"不是这个，别再提示"）是同一类概念；新模块自己维护文件，不去依赖那份缓存。

### 来源信息（【我的提议】，只作辅助列）

- 读 `文件名:Zone.Identifier` 备用数据流，优先 `ReferrerUrl`，没有则回退 `HostUrl`；只保存和显示**域名**，不保存完整 URL，不上传。
- `about:internet` 是占位值，要识别并忽略，不能当域名解析。
- 没有该数据流的文件，来源留空。
- 实测覆盖率差异很大（作者机器：压缩包 15/15，安装包 3/39，PDF 6/6，图片 6/8），所以不能用来源做分类规则的条件。
- 域名只作显示和提示（例如 `github.com`、非常规下载站），**不据此判断文件是否有害**。

### 免费 / Pro

【定】MVP 全部免费，包括撤销。以后可能放进 Pro 的候选：自定义规则、规则导入导出、后台监控、定时。具体分界线等 MVP 验证后再定。

## 留给施工者决定

- 下载文件夹里已有"另一种语言命名的同类文件夹"（例如 Mouzi 建的 `Documents`、`Installers`）：复用、新建还是让用户选？
- 顶层子文件夹在回顾里怎么算年龄：子树里最新文件的时间（准确但可能慢，需要上限），还是文件夹自身的时间（文件夹修改时间只反映直接子项的增删，不可靠）。
- 同名冲突比较内容时对大文件的哈希策略（先比大小和前若干字节再全量哈希？）。
- 日志保留多久，清理策略。
- 扫描的并发与取消，以及大目录下的响应性。
- "最近写入不足 N 分钟"这个 N 是否可调。
- 桌面右键菜单里的"分析此文件夹"入口，是否也要加"整理此文件夹"（MVP 不要求）。
- 第一次 Store 提审时，"移动用户文件"这类行为是否需要额外的说明文字。

## 后续（不在本设计范围内，列出以便取舍）

- **只收集、不移动的后台监控**：新文件进入"待批准"队列，由用户确认（Mouzi 的"手动（仅收集）"模式已经这么做）。需要托盘、开机启动、文件系统监视；现有 `LeftoverWatcher` 只是对已知路径的短时间轮询，**不能当作监控器复用**。
- **"已安装软件的安装包"提示**：例如 `Zotero-9.0.5_x64_setup.exe` 对应的软件已安装，提示可清理。依赖对已装软件列表做模糊匹配，误判风险高，只能做"建议"，不能自动勾选；动手前应先用作者 `Installers` 里的 39 个文件试一下命中率。
- 简体中文用户的声音仍是缺口：小红书只读到少量标题和 2 条评论，V2EX 只读到 2 个帖子。上线前最好再补一轮。

## 已知风险

- 本设计的"用户想要的是习惯而不是一次性整理"这一判断，证据很弱；如果上线后回顾区几乎没人用，需要回头调整。
- 免费竞品（Mouzi、国内管家软件自带的整理功能）较多，MVP 全免费意味着短期内没有收入，只换取曝光；这与 `2026-10-24` 设计里"免费获客"的策略一致，但没有证据表明这个模块本身能带来转化。
- "回顾"里有约四成文件超过阈值，列表可能很长；如果默认展示方式不当，会重蹈"用户学会忽略"的覆辙。施工时要优先验证列表的可用性。
